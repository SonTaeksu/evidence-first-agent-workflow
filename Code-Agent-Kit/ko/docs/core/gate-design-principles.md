# Gate 설계 원칙

이미 동작하는 검사를 죽이지 않으면서 새 결정적 검사를 추가하는 방법.

`enforcement-matrix.md`는 각 Rule이 무엇을 강제하는지 기록합니다. 이 문서는 검사가 그 표에 오르기 전에 만족해야 할 것을 기록합니다.

제안이 아닙니다. 폐쇄망에서 소형·중형 로컬 모델로 **실사용 12세션**을 관찰해 얻은 실패에서 역산한 것이고, 배운 순서대로 적었습니다.

## 왜 이 원칙들이 있나 — 관찰된 3가지 사실

아래 모든 Rule이 이 셋 중 하나에서 나옵니다. 이 Workflow를 적용할 때는 그 전제가 자기 환경에서도 유효한지 먼저 확인하세요.

### 사실 ①. 문서에 적어도 안 읽는다 — 모델 급과 무관하다

모델은 Rule을 읽고도 위반했습니다. 최악의 관측 사례: Project 문서에 "이 Project에는 공용 Library가 없으니 그 함수를 호출하지 말 것"이라 적혀 있었고 모델이 **그 File을 읽었는데**, 호출이 정의돼 있지 않다는 이유로 **그 함수를 직접 만들어 채웠습니다.** 지어낸 File이 Build를 깨뜨렸고 6회 연속 실패했습니다.

문서 정확도를 높이는 것으로는 해결되지 않습니다. 기계가 잡아야 합니다.

### 사실 ②. Context 압축이 Rule을 지운다

관측 환경은 64k Context에 ~50k 자동 압축이었습니다. 12,811행 Session에서 지식 조회는 **2회, 그것도 6,778행째**였습니다 — 그 앞은 전부 기억으로 작업했습니다. 초반에 가져온 15KB 문서는 Code를 쓸 시점엔 이미 사라져 있고, 그래서 "문서 읽고도 훈련 습관으로 회귀"가 반복됩니다.

| Rule이 있는 자리 | 압축 후 | 결론 |
|---|---|---|
| System Prompt에 상주하는 `AGENTS.md` | **생존** | 비협상 Rule은 여기에, **짧게** |
| Session 중에 가져온 문서 | **소실** | 상세·Reference 전용. Rule을 여기에 의존하지 말 것 |
| CLI 검사 · git Hook | **무관** | 최강. 옮길 수 있으면 옮긴다 |

### 사실 ③. "완료" 자기보고는 믿을 수 없다 — 위험한 형태는 실패의 합리화다

관측: Compile 통과 → "완료"인데 Runtime 의존성 누락으로 실행 시 크래시. Test 6/6 통과 → "완료"인데 Test Harness가 경로 접두를 안 태워 실서버는 404. Generator가 `Success 46, Fail 1`을 냈는데 모델이 **"그 File은 형식이 달라서 정상"**이라 적고 완료 선언 — 실패 원인은 자기가 만든 File이었습니다. 설치는 33개 중 6개만 쓰고 "설치 완료"라 보고했고, 받아보지도 않은 File을 "확인 완료"로 기재했습니다.

그래서 Rule은 "실패를 놓치지 말라"가 아닙니다. **"실패를 설명으로 정상화하지 말라"**입니다. 그리고 그 뒤에는 개수·해시 대조 같은 기계 판정이 있어야 합니다.

## 원칙

### 1. 문서는 강제하지 못한다 — 기계 판정으로 옮긴 것만 지켜졌다

프로그램으로 옮긴 Rule은 지켜졌습니다. 산문으로 남은 Rule은 모델이 읽었든 아니든 지켜지지 않았습니다. 모든 Rule을 검사로 옮길 후보로 보고, 산문은 옮길 수 없는 것의 Fallback으로 다루세요.

### 2. 확실한 것만 BLOCK

오탐이 한 번 나면 개발자가 `--no-verify`를 쓰기 시작하고, 그 뒤로는 Hook 전체가 무력합니다. 거짓 경보의 비용은 낭비된 1분이 아니라 가진 검사 전부입니다.

```text
ADVISORY
→ WARN (실제 작업에서 관측)
→ BLOCK (오탐 0 확인)
```

승격은 이 순서로만.

### 3. 애매하면 WARN — 단, 가장 위험한 것이 가장 약하게 막히는 상태를 경계하라

원칙 2를 단순 적용하면 의심스러운 것을 전부 WARN으로 내리게 되고, 그러면 사소한 것은 BLOCK인데 치명적인 것은 경고에 그치는 표가 만들어집니다.

**침묵 실패는 BLOCK이어야 합니다.** 시끄러운 실패 — Build 오류, 예외, 눈에 보이는 Stack Trace — 는 다른 것이 드러내 주므로 WARN이어도 됩니다. HTTP 200에 0건을 돌려주거나, 빈 화면을 그리거나, 아무것도 안 하고 exit 0을 내는 실패는 드러내 줄 것이 없습니다. **확실하다는 것이 BLOCK의 근거이고, 관측되지 않는다는 것이 BLOCK이어야 하는 이유입니다.**

### 4. 탈출구는 명시적 Marker로만 — 암묵 면제는 금지

모든 검사에는 출구가 필요합니다. 없으면 첫 번째 정당한 예외에서 죽습니다. 그러나 그 출구는 사람이 Source에 적은 **의도 선언**이어야 합니다.

```text
// gate:allow-rest   ← 누군가 의도를 적었으므로 면제
```

정황을 근거로 면제하지 마세요 — "File이 이미 있으니까", "값이 비어 있지 않으니까", "이 디렉터리는 생성된 것 같으니까". 암묵 면제는 그것이 허용하려던 결함과 구분되지 않고, 조용히 넓어져서 검사가 아무 의미도 없어집니다.

### 5. Rule ID는 모델이 아니라 Tool의 소유다

모든 인수기준에 안정 ID를 부여하고, **실패할 때 검사가 그 ID를 출력**하게 하세요. 모델에게 자기 출력에 ID를 태깅하게 하거나 어떤 Rule을 만족했는지 선언하게 하지 마세요 — 그 단계는 건너뛰어지고, 소형 모델은 항상 건너뜁니다.

그러면 모델의 협조 없이 추적성이 성립합니다. 가질 가치가 있는 추적성은 그것뿐입니다.

### 6. 판정 근거는 모델의 머리가 아니라 Project 문서에 둔다

"이 Project가 X를 쓰는가"를 모델이 판단해야 하는 검사는, 다음번에 다르게 판단하는 것으로 모델이 걸어서 우회할 수 있는 검사입니다. 그 결정을 Project Map이나 동등한 State 문서에 **한 번 기록**하고, 검사가 그것을 읽게 하세요.

기록된 의도가 기준이면 판정이 어제와 오늘 같고, 모델이 다른 경로로 같은 실수에 도달해도 잡힙니다.

### 7. 판단 단계를 없애면 실행률이 오른다

어떤 File을 넘길지 운영자가 골라야 하는 검사는 실행되지 않습니다. 관측: 12세션 동안 검사 실행이 사실상 0회였고, 이유는 인자를 정하는 것 자체가 하나의 단계였고 그 단계가 건너뛰어졌기 때문입니다.

해법은 **인자 없이 도는 Runner**이고, 기본값은 명백한 범위 — 마지막 검사 이후 바뀐 File — 입니다. 필요하면 명시적 Flag로 넓히세요. 없앤 판단 하나하나가 검사를 더 이상 건너뛸 수 없는 자리가 됩니다.

### 8. Compile·Test 통과는 동작이 아니다

Compiler는 Runtime 의존성을 검사하지 않습니다. Test Harness가 실제 배포가 쓰는 경로를 태우지 않을 수 있습니다. Artifact·Rendered Output·Runtime을 별도 Layer로 기록하고, 하나가 다른 하나를 대신하게 두지 마세요. 실행할 수 없었던 Layer는 이유와 함께 `PENDING`입니다. 절대 `PASS`가 아닙니다.

### 9. 내 산출물도 같은 실패를 한다

이 Rule들을 강제하는 킷 자신이 그 Rule들을 반복해서 어겼습니다. Template을 복사하고 갱신하지 않은 것이 두 번, Step 번호 중복, 모호한 문구가 하류에서 Build 실패를 유발.

두 가지가 따라 나오고, 선택 사항이 아닙니다.

- **산출물은 다시 읽는 것이 아니라 실측으로 검증한다.** 개수·크기·해시를 대조하세요.
- **문서는 diff와 카운트로 생성한다.** 사람이든 모델이든 손으로 옮겨 적는 숫자는 문서가 조용히 낡는 자리입니다. 숫자를 적어야 한다면 실측할 수 있는 규칙을 함께 기록해서, 그 주장이 검사 가능하게 만드세요.

킷이 복사하라고 지시한 Template이 수정 없이 킷 자신의 Validation을 통과해야 하는 이유도 이것입니다. 통과하지 못하면 유일한 출구가 Gate 우회이고, 실패 메시지가 그 방법을 친절히 안내합니다.

## 한계를 감추지 말고 공개하라

어떤 Rule은 어떤 프로그램으로도 검사할 수 없습니다. "5단계를 출력했는가" "시작 전에 동기화했는가" "추측하지 않고 실제로 File을 읽었는가" — 마지막 것은 관측된 **최다 위반 Rule**이고, 어떤 산출물로도 검증할 수 없습니다.

**그 한계를 공개 문서에 그대로 적으세요.** 감추면 얻는 것은 없고 신뢰를 잃습니다. Enforcement Matrix의 ADVISORY 구간은 부끄러운 것이 아니라 **커버리지 구멍의 목록**이고, 그것은 다음 Tool의 Roadmap과 같은 것입니다.

구조적 벽 셋이 남아 있고, 여기 어떤 원칙도 그것을 없애지 못합니다.

- **검사는 무언가가 발동시켜야만 자동으로 돕니다.** 커밋을 안 하거나, Hook을 설치하지 않았거나, 저장소 루트 밖에서 작업하면 그대로 샙니다. 수동 실행의 마찰을 줄이는 것은 도움이 되지만 구멍을 막지는 못합니다.
- **CI가 없으면 비협조적인 모델을 이길 방법이 없습니다.** CI가 가능하면 push·PR에서 전체 검사를 돌리는 것이 협조에 의존하지 않는 유일한 수단입니다. CI 예제를 함께 배포하세요.
- **Context 압축은 Tool로 못 막습니다.** 항상 상주하는 Rule을 짧게 유지하는 것이 유일한 방어이고, 그래서 Rule을 추가할 때마다 그 File이 압축을 못 견딜 만큼 비대해지는지 따져야 합니다.

## 적용

`enforcement-matrix.md`에 검사를 추가하기 전:

- [ ] 산문이 지켜내지 못해서 프로그램으로 옮긴 Rule이다 (원칙 1)
- [ ] 판정이 결정적이고 문구·File 명명에 좌우되지 않는다
- [ ] 알려진 정상 산출물을 돌려 발견 0건을 확인했다
- [ ] 침묵 실패는 BLOCK하고, 시끄러운 실패는 WARN이어도 된다 (원칙 3)
- [ ] 면제 경로가 명시적 Marker이고 암묵 면제가 없다 (원칙 4)
- [ ] Tool이 Rule ID를 스스로 출력한다 (원칙 5)
- [ ] 판정 근거가 모델 판단이 아니라 Project 문서다 (원칙 6)
- [ ] 흔한 경우에 Runner가 인자를 요구하지 않는다 (원칙 7)
- [ ] Self-test가 통과 Fixture와 의도적 실패 Fixture를 모두 덮는다
- [ ] Runner가 필요한 인자를 실제로 넘기는 것을 실행해서 확인했다
- [ ] Exit Code는 통과 `0`, Validation 실패 `2`, Tool 오류 `1`
- [ ] Severity가 근거에 맞고, BLOCK은 오탐 0을 확인한 뒤에만 주장한다
- [ ] 이 검사가 여전히 못 잡는 것을 빼지 말고 ADVISORY 구간에 적었다
