# Finding 식별자

모든 검사는 실패할 때 자기 식별자를 출력합니다. 모델에게 어떤 Rule을 만족했는지 선언하게 하지 않습니다.

## 규칙

```text
<도구 디렉터리 이름>:<finding-id>
```

```text
check-shell-safety:ps1-bom
check-mirror-parity:orphan-path
check-stack-readiness:missing-document
csharp-winforms/designer-spec:missing-control
```

Namespace는 도구 디렉터리 이름입니다. 도구 디렉터리는 이미 유일하므로 두 검사가 충돌할 수 없고, 자기 Validator를 싣는 Stack Pack이 중앙 할당을 받을 필요가 없습니다.

## 왜 모델이 아니라 Tool이 소유하나

모델에게 자기 출력에 Rule을 태깅하게 하는 것은 하나의 단계이고, 단계는 건너뛰어집니다 — 소형 모델은 이 단계를 매번 건너뜁니다. **Tool이** 출력하는 식별자는 모델의 협조 여부와 무관하게 살아남고, 가질 가치가 있는 추적성은 그것뿐입니다.

이것이 없으면 불가능한 기계 검사가 둘 있습니다.

- **문서에는 있는데 구현이 없음.** `enforcement-matrix.md`에 올라 있는데 어떤 Tool도 그 식별자를 내지 않는 Rule은 **돌지 않는 Rule**입니다. 표는 강제된다고 말하는데 강제하는 것이 없습니다.
- **구현은 있는데 문서가 없음.** Tool이 내는데 어떤 matrix 행에도 없는 식별자는 문서화되지 않은 판정입니다 — 운영자는 실패를 보고도 그게 무슨 뜻인지 찾을 방법이 없습니다.

둘 다 식별자가 없던 시절에 실제 결함으로 관측됐습니다. 올바르게 도는데 식별자를 안 내놓아 어떤 Rule인지 추적할 수 없던 검사가 있었고, 핸드오프 문서에만 있고 matrix에는 세 릴리스 동안 없던 Rule이 있었습니다.

## finding id 작성법

- 소문자, 하이픈, 공백 없음
- **조건**을 이름으로 삼습니다. 해결책이 아닙니다 — `orphan-path`이지 `add-missing-file`이 아닙니다
- 안정적이어야 합니다. **개명하지 마세요.** 자기설명적인 식별자는 개선하고 싶어지는데, 개명 한 번이 그것을 참조한 모든 문서·Worklog·면제를 깹니다. 이름이 잘못됐다면 더 나은 것을 추가하고, 참조가 사라질 때까지 옛 것도 함께 출력하세요

## 실패 줄 형식

```text
<경로>:<행>: [<도구>:<finding-id>] <무엇이 잘못됐나> — <왜 문제인가>
```

식별자를 대괄호에 넣어 기계로 뽑을 수 있게 합니다. 그 뒤는 사람이 읽는 부분입니다.

## 대괄호 접두는 계약이다

실패 줄 맨 앞의 `[<tool>:<finding-id>]`는 서식이 아니라 **안정된 인터페이스**입니다. 다른 도구가 이것을 읽습니다. 형식을 바꾸거나, 식별자 없이 실패를 출력하면 그 소비자들이 깨집니다.

여기서 의무 두 가지가 나옵니다.

**기계 소비자는 식별자를 매칭하고, 산문은 절대 매칭하지 않는다.** 대괄호 뒤의 모든 것은 읽는 사람을 위한 것이고 언제든 문구가 바뀔 수 있습니다. 문장을 매칭하는 소비자는 누군가 그 문장을 개선하는 순간 조용히 죽고, 지켜보는 것이 없습니다 — 검사는 계속 exit 0을 내며 건강해 보입니다.

가정이 아닙니다. `check-kit-selfcheck`는 readiness 검사기의 실패를 산문 접두사(`"Missing or empty required document:"`)로 분류했습니다. 검사기 메시지가 식별자를 갖게 되자 모든 접두사가 더는 일치하지 않게 되었고, 시드 판정이 완전히 부화(不化)했습니다: 시드에서 필수 문서를 지워도 세 릴리스 내내 CLEAN, exit 0. 자기 self_test가 이걸 잡고 있었습니다. 아무도 self_test를 돌리지 않았습니다.

**형식 변경은 소비자 전수 갱신이 끝나야 완료다.** 소비자를 찾는 것은 추측이 아니라 조사입니다:

```bash
grep -rn "startswith(\|importlib\|\.stdout" --include=*.py tools/
grep -rn "grep\|Select-String" --include=*.sh --include=*.ps1 --include=*.yml .
```

애초에 파싱하는 소비자를 두지 않는 것이 낫습니다. 어떤 도구가 다른 도구의 판정을 필요로 한다면, 내부를 import 하는 것보다 하위 프로세스로 호출해 출력에서 식별자를 읽는 편이 낫습니다. CLI는 모든 에이전트·훅·CI가 실제로 쓰는 층이므로 그것을 상시 실행하면 이 계약이 정직하게 유지되고, import 한 함수는 아무도 의존하지 않는 시그니처에 결합되며 — `.ps1` 양벌로는 애초에 미러링이 불가능합니다.

## 식별자가 아닌 것

식별자는 Severity가 아닙니다. `check-shell-safety:ps1-bom`은 BLOCK이지만 같은 Tool의 다른 finding은 WARN일 수 있습니다. Severity는 `enforcement-matrix.md`에서 식별자 옆에 적습니다.

식별자는 그 검사가 옳다는 보증이 아닙니다. 그 검사를 지칭하는 손잡이입니다.

## 양벌이 일치하는지 검증

같은 검사의 `.py`와 `.ps1` 구현은 같은 입력에 **같은 종료코드와 같은 식별자 집합**을 내야 합니다. 종료코드만 비교하는 것으로는 부족합니다 — 두 구현이 서로 **다른 이유로** 각각 2를 내도 동일해 보입니다.

```bash
python tools/check-script-parity/check_script_parity.py --root .
```
